# 本地骨架、工作人员诊断与回滚

服务 1.1.0 配套 Android 1.2.0。日常训练为相机本地预览＋上传识别＋关键点返回。Android 默认显示骨架，可切换纯本地画面；切换不协商新连接、不修改会话和计数。采集请求仍为 640×480、15 FPS。

## 显示与诊断

准备阶段只有本地视频。识别后在本地视频上绘制 COCO-17 人体与 MediaPipe-21 手点，使用与播放器相同的等比例留白、方向和镜像。没有缓存视频等待识别，也不预测或补帧，骨架会随上传和推理产生短暂滞后。

连续 300 ms 没有可用更新即清除骨架。已校准时还按服务端时间丢弃过时结果；无法校准时按本地接收时间清除。旧会话、旧序号、越界或非有限坐标不绘制。桥接/预测手点不显示为新检测。原有 3 秒结果中断提示、10 秒训练中断继续工作。

工作人员登录后，在“设置 → 设备与服务”开启“下一次训练开启远端诊断”。下一次成功连接后开关自动复位；退出登录、重新登录或切换服务会清除。该次训练出现“工作人员诊断”入口，可查看服务端解码后、未绘制骨架的视频，或按需查看一张无损 PNG。远端视频仍有回传压缩；PNG 可帮助判断失真是否已存在于上传图像中。患者请求诊断返回 403，不能占用训练名额。

普通模式不创建回传视频轨和发送任务，Android 不接收或解码回传视频。诊断只能在下一次训练前启用，当前训练不新增视频协商。

## Qt 本地显示

Qt 继续在本机推理，摄像头线程独立显示镜像原始视频；识别线程只处理最新待处理帧，调用 `PoseEngine.process(..., draw=False)`。UI 复用 `pose_message` 的归一化坐标与跟踪状态，在 `desktop/skeleton_view.py` 使用 QPainter 绘制骨架，等比例留白和镜像与原图一致。预测/桥接手点不显示，距采集时间超过 300 ms 的结果不绘制；切换动作立即清空旧骨架并丢弃旧动作结果。

Qt 与 Android 使用各自原生绘图库，共用关键点格式和显示规则；Qt 不经过 Android 或 WebRTC。Qt 的相机分辨率设置保持原值，不随 Android 的 640×480 改动。原 `draw=True` 标注绘制路径保留给现有工具及需要标注图像的调用，本次未删除。

## 骨架协议

客户端创建 `pose` DataChannel，`ordered=false, maxRetransmits=0`。服务端发现发送缓冲未清空时跳过本次骨架，避免排队。业务、停止、汇总与确认保留在可靠 `rehab` 通道。

骨架消息包含：

| 字段 | 定义 |
| --- | --- |
| type/version/session_id/seq | pose、1、当前会话、递增结果序号；序号可因丢弃而不连续 |
| width/height/rotation | 服务端解码图像尺寸；坐标基于解码后正向图像，rotation 固定 0 |
| decoded_at_ms/completed_at_ms | 服务端取出已解码帧、结果生成时的单调时钟毫秒 |
| body/body_state | 17 项 `[x,y,confidence]`；无效点为 null；状态 fresh/cached/missing |
| hands | 左右侧、state、predicted、21 项 `[x,y]`；非 fresh 或 predicted 时 points 为 null |
| tracking_confidence | 原有跟踪状态指标；不作为医学置信度 |

坐标 x/y 归一化至 0–1，按人体左右命名，显示镜像不改变算法输入。手模型目前不输出逐点分数，hands.confidence 为 null，不编造概率。人体仍沿用原有每两帧更新一次的行为，cached 状态可能增加可见滞后。

`rehab` 上发送 `{type:"clock_ping",client_ms:<Android单调时钟>}`，服务端返回同一 client_ms 与 server_ms，附会话 ID。Android 根据往返中点估算时钟偏移，优先较小 RTT 样本，定期刷新。解码帧到本地绘制的估计包含取帧后的等待、识别、结果传输及本地调度，不包含采集、上传或服务端取到该帧之前的延迟；时钟误差约为校准 RTT 的一半。校准不可用显示 `--`。RTT 不等于画面延迟。

## 验证与采样

`tests/test_skeleton.py` 检查坐标序列化和诊断权限；`tests/test_rtc.py` 通过真实 ICE/数据通道验证普通模式无视频发送、诊断原图/PNG、时钟及可靠结束。Android `SkeletonOverlayTest` 检查留白、镜像、横竖尺寸、过时结果和预测点；`TrainingPerformanceTest` 对真实连接采样并断言显示切换不更换连接/会话。

`tools/benchmark_videos.py` 固定六个教学视频的帧、时间戳和 640×480 输入。`tools/benchmark_robot.py` 默认仅 rub/fist，每段 15 秒预热＋30 秒采样，三次重复。长基线保留全部原始数据，但比较统一取预热后前 30 秒。工具只连接显式指定的独立 18121 端口；服务端用独立 REHAB_DB，关闭 SMTP 环境配置，使用测试账号。

可选 `REHAB_PERFORMANCE_DIR` 将服务端逐帧采样写入独立 JSONL 文件，默认关闭；写入失败不打断训练。骨架和性能数据不写入患者业务数据库，schema 保持 3。`tools/compare_benchmarks.py` 验证固定输入一致性，导出 summary.json 与 metrics.csv，包含中位数、P95、最小值和最大值。Android CPU 百分比以单核为 100%；RTC 字节率为载荷，不是 Wi-Fi 总流量。

机器人系统曾在仪器测试方法完成、训练结果保存后从外部强停测试进程，旧版与新版均出现。工具仅在完整采样、已保存 completed 结果、方法已报告完成，并核实系统退出原因为相应时间的 USER REQUESTED 后保留性能数据并继续；记录 runner 异常，不将它计为 JUnit 完整通过。训练中断、断言失败、原生崩溃及不完整数据仍停止测试。

本轮仅对 rub/fist 做真人性能对照，六动作保留固定视频回归。结果及复测限制见 [640×480 性能报告](performance_640x480.md)。出现具体帧率异常时可用 `--modes skeleton` 等只复测相关模式，输出到独立 `robot-after-retest/`，保留原样本；汇总工具将两组分列。

## 两端部署与回滚

更新服务源码后重启原服务，再安装配套 APK。训练前确认 health 能力为 true；仅替换磁盘源码不会升级已运行进程。新 App 遇到旧服务提示升级，不自动恢复日常视频回传。

交付保留原安装 APK、两端原始 Git 归档、模型/教学视频哈希、新版与回滚 APK。回滚步骤：

1. 结束训练并停止服务，备份当前业务库；不删除 App 数据，不卸载。
2. 用基线服务源码启动同一业务库；两版均为 schema 3，无需数据库降级。
3. 覆盖安装同证书的 `复健-1.1-rollback.apk`。它使用基线源码，仅把 versionCode 提高至 3，避免 Android 阻止从新版 code 2 降级；行为为原版视频回传。以后再次升级需使用 versionCode 大于 3 的构建。
4. 保留原服务地址和登录资料，确认 health、视频、计数及结果保存。

原始安装 APK 的 code 为 1，不能假定正式包允许 `adb install -d` 降级。业务库只在数据损坏时使用另存备份恢复，不为显示回滚覆盖已有训练记录。
