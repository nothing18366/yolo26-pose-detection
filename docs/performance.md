# 性能与验证结论

当前组合为服务端 1.2.0、Android 1.3.0，640×480、请求 15 FPS。测试设备为 RK3588/Android 12，服务端为 Mac CPU；结果不代表 Jetson。真人动作准确率与完整摄像头到屏幕延迟均未完成标注或外部拍摄测量。

## 两种日常模式

2026-10-29，每条链路预热 15 秒、有效采样 15 秒、一次，实际相机约 30 FPS。场景未经标准化，手部入镜和补检次数不完全相同，不能据此判断某模式更跟手或 CPU 必然更低。

总处理 P95 来自有效窗口服务端逐帧记录；其余来自约每秒 App 采样。带宽为 RTC 视频载荷，不含全部 Wi-Fi/UDP/SRTP 开销，数据通道另计。诊断采样时显示本地骨架，同时回传原图；诊断播放器在独立流程中验证。

已确认本地骨架无回传视频解码、服务端绘制为零；远端标注无 pose 通道和本地骨架绘制，增加约 1.26 Mbps 视频下载。远端标注采样方法完成且 completed 结果保存后被系统外部强停，因此该段不记完整 JUnit 通过；之后独立的模式切换、断流回退/手动恢复与诊断覆盖/下一动作恢复测试完整通过。

## 当前识别配置的依据

正式使用 MediaPipe IMAGE。既有同模型 VIDEO 实验改变了握拳合格数与点按计数；单次真人反馈差别不大，且处理 P95 增大，未通过替换条件。保留六动作标准，不用改阈值抵消模型模式差异。

上传沿用原发送器默认值。既有 20 FPS 短测降低了编码量与 App CPU，但估算骨架延迟中位数仅改善约 3–4 ms，摩擦手背服务端 FPS 下降约 11.4%，P95 未改善，因此没有采用限帧。设备实际采集与请求 FPS 不一定相同。

平滑前显示点与动作平滑数据已分离；全图手检测与人体检测并行，外展仍使用原顺序裁剪。既有单次握拳/移动对照中，并行后解码→绘制中位数估计从 97.6 降至 83.3 ms，用户反馈改善；真人输入不完全一致，不能保证其他硬件有相同比例收益，也不能据此宣称 CPU 或温度下降。

## 回归与边界

- 六个教学视频共 3,432 帧：纯绘制、显示点分离、并行及实验入口清理前后，人体/手点、阶段、计数及合格判定一致（绝对误差 1e-6）。计数 rub=0、fist=8、stretch=0、cup=0、abduction=0、press=4，仅作为固定输入回归输出，不是准确率。
- 自动化覆盖六动作、推理/显示边界、三条 RTC 路径、骨架有效性与权限、账号/计划/反馈、教学、可靠保存与令牌失效。Android 覆盖骨架映射/时效、偏好跨登录、模式能力检查；实机模式切换和诊断一次性覆盖已验证。
- 未完成六动作真人准确率、长期热稳定性、完整画面延迟、Jetson 及旧 Android API 兼容验收。部分实体仪器运行器曾在方法完成后被系统 USER REQUESTED 强停，需分别保留“完整采样”和“完整 JUnit 通过”的结论。

历史原始采样与旧构建已按维护要求清理，保留上述测量摘要，不据此声称可重新计算全部历史结果。新的性能比较应使用同设备、机位、光照、网络与输入，保留原始记录、异常和重复次数，不只报告最好结果。
